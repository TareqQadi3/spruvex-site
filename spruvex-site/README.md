# SpruVex R — الموقع التسويقي

موقع تسويقي لمنتج **SpruVex R** (نظام إدارة مطاعم SaaS / POS) — Next.js (App Router) +
TypeScript + Tailwind CSS، بدون CMS خارجي، المحتوى والأسعار ثابتة بالكود.

## المكدس التقني

- **Next.js 16 (App Router)** + TypeScript + Tailwind CSS v4
- **framer-motion** للحركة والتفاعلات الدقيقة، **lucide-react** للأيقونات
- **better-sqlite3** كقاعدة بيانات محلية بسيطة لهذه المرحلة (انظر تحذير النشر أدناه) —
  يتطلب **Node ≥ 22** تحديدًا (`engines.node` بـ`package.json`)
- **zod** للتحقق من المدخلات، **jose** لجلسة الإدارة (JWT موقّع)

⚠️ **كل حزم `devDependencies` منقولة إلى `dependencies` عمدًا** (TypeScript، ESLint،
Tailwind، كل `@types/*`) — `next build` يشغّل type-checking + ESLint + PostCSS
فعليًا، فهي حزم بناء حقيقية لا تطوير فقط. منصات نشر كثيرة (منها Render) تضبط
`NODE_ENV=production` أثناء `npm install` أيضًا، وnpm يتجاهل `devDependencies`
تلقائيًا في هذه الحالة — لو بقيت هذي الحزم بـ`devDependencies` فسيفشل البناء هناك
بخطأ "module not found" لكل حزمة منها بالتتابع. **لا تُعِد أيًا منها لـ`devDependencies`.**

## التشغيل محليًا

```bash
npm install
cp .env.example .env.local   # ثم عبّئ القيم (انظر الجدول أدناه)
npm run dev
```

- `npm run build && npm run start` لتشغيل نسخة إنتاج محليًا.
- `npm run lint` للتحقق من الكود.

## متغيرات البيئة (`.env.local`)

| المتغير | الوصف |
|---|---|
| `ADMIN_PASSWORD` | كلمة مرور الدخول للوحة `/admin`. استخدم قيمة عشوائية طويلة، لا تضعها بالكود أبدًا. |
| `ADMIN_SESSION_SECRET` | مفتاح توقيع جلسة الإدارة (JWT)، 32 حرفًا فأكثر. يمكن توليده بـ `openssl rand -hex 32`. |
| `SPRUVEX_R_API_URL` | رابط API الأساسي لمشروع spruvex-r (بدون `/api/v1`). مطلوب لتفعيل التجربة المجانية فعليًا. |
| `SPRUVEX_SITE_API_KEY` | سر مشترك مع spruvex-r — **يجب أن يطابق حرفيًا** متغير `SPRUVEX_SITE_API_KEY` هناك (يُضبط يدويًا بكلا الطرفين، لا مزامنة تلقائية). |

لا تُرفع `.env*` لـ git (مضبوط في `.gitignore`). راجع `.env.example` كنقطة بداية.

    api/                   Route Handlers (trial-signup(+verify/resend-otp), payment-submission, admin/*)
  components/
    layout/  home/  pricing/  forms/  admin/  ui/
  hooks/                   useCountUp, useCountdown
  lib/

    db.ts + repositories/  طبقة قاعدة البيانات
    validation.ts          مخططات Zod (تحقق جوال سعودي، بريد، إلخ)
    spruvexR.ts             عميل استدعاء spruvex-r من جانب السيرفر فقط (تفعيل التجربة الفعلي)

  proxy.ts                 (middleware): حماية /admin، كوكي CSRF، رؤوس أمان

**التوسّع لاحقًا لتطبيق ERP منفصل**: لم يُبنَ أي شيء الآن، لكن البنية لا تُقفل عليه —
يمكن لاحقًا إضافة `src/app/erp/` كمجموعة مسارات مستقلة تمامًا (أو نطاق فرعي منفصل يوجَّه
لنفس المشروع أو لمشروع Next.js آخر) دون أي تعارض مع ما هو موجود، لأن كل شيء هنا
(الثوابت، المكوّنات، الـ API) مقصور على نطاق مسارات SpruVex R التسويقية الحالية.

## نظام الأسعار والباقات

كل الباقات/الميزات/الإضافات مصدرها **ملف واحد فقط**: `src/lib/constants.ts`.
لتعديل سعر أو ميزة، عدّل هذا الملف فقط — لا تكرّر الأرقام في أي مكوّن.

⚠️ **قيم Placeholder تحتاج اعتماد رسمي من صاحب المنتج قبل الإطلاق**:
- سعر دورة **6 أشهر** لكل باقة (لم يُحدَّد في بيانات المنتج — محسوب مبدئيًا بخصم ~10%).
- أسعار **الإضافات الأربع** (فرع إضافي، تكامل توصيل، بوابة دفع المنيو، تنبيهات واتساب).
- **بيانات التحويل البنكي** (`BANK_TRANSFER_INFO` في `constants.ts`): اسم البنك/الحساب/الآيبان
  كلها قيم `TODO` مؤقتة — يجب استبدالها ببيانات الحساب البنكي الفعلي قبل الإطلاق.

## نظام الاشتراك — حالة هذه المرحلة (مهم)

### 1) التجربة المجانية (`/contact` → `POST /api/trial-signup`) — تفعيل فعلي حقيقي

يُخزَّن الطلب أولًا في جدول `trial_signups` المحلي (سجل احتياطي/متابعة مبيعات يبقى
دائمًا)، ثم يُستدعى `POST {SPRUVEX_R_API_URL}/api/v1/public/trial-signup` فعليًا
(عبر `src/lib/spruvexR.ts`، من جانب السيرفر فقط) — نفس المسار الذي ينشئ Tenant
حقيقي بـ spruvex-r بحالة تجريبية 14 يوم، يستخدم `provisionTenant()` الحقيقي هناك،
لا منطق موازٍ.

- **نجح الاستدعاء** → السجل المحلي يُعلَّم `provisioned` مع `tenant_id`/`dashboard_url`،
  والمستخدم يرى خطوة تحقق OTP (`/api/trial-signup/verify` → `POST /auth/register/verify`
  بـ spruvex-r، **نفس** المسار الذي يستخدمه أي تسجيل ذاتي عادي هناك) ثم يُحوَّل مباشرة
  لرابط لوحة التحكم الحقيقي عند نجاح التحقق.
- **جوال أو بريد مسجّل مسبقًا** (409 حقيقي من spruvex-r، أو فحص محلي مسبق لبريد سبق
  تفعيله) → لا تُعرض رسالة "سيتم التفعيل خلال ساعات" المُضلِّلة هنا؛ يُعلَّم السجل
  `duplicate` وتظهر رسالة دقيقة "لديك حساب مسجّل بالفعل".
- **فشل حقيقي آخر** (شبكة/تهيئة/5xx) — بعد استنفاد محاولتين إضافيتين تلقائيتين لفشل
  الشبكة/5xx تحديدًا (`createSpruvexRTrial` بـ`src/lib/spruvexR.ts`؛ لا إعادة محاولة
  لـ401 تهيئة أو 409 تكرار) → لا تفشل تجربة المستخدم: السجل يُعلَّم `manual_review`،
  تظهر رسالة "سيتم تفعيل حسابك خلال ساعات"، والخطأ الحقيقي يُسجَّل بوضوح بسجلات
  السيرفر (`console.error`) لمتابعته يدويًا. لوحة `/admin` تعرض حالة كل طلب مع رابط
  مباشر للوحة المطعم عند نجاح التفعيل.
- **`POST /api/trial-signup/resend-otp`**: إعادة إرسال رمز التحقق (يُستدعى إن انتهت
  صلاحية الرمز الأول قبل أن يُدخله المستخدم) — وسيط بسيط لـ
  `/auth/register/resend-otp` بـ spruvex-r.

**بريد Resend (`src/lib/email.ts`، best-effort دائمًا — فشل الإرسال لا يُفشل التدفق):**
- بريد **تنبيه إدارة** (`ADMIN_ALERT_EMAIL`) عند كل محاولة تسجيل جديدة (أي نتيجة:
  تفعيل/مراجعة يدوية/تكرار).
- بريد **ترحيب** (يحمل `dashboardUrl`) فور نجاح التحقق من رمز OTP فعليًا في
  `/api/trial-signup/verify`.
- ⚠️ **بريد "رمز التحقق" نفسه لا يُرسل من هنا** — العميل لا يملك الرمز الفعلي في
  الإنتاج أصلًا (`OtpService.issue()` بـ spruvex-r يُرجعه فقط خارج `NODE_ENV=production`،
  عمدًا حتى لا يتسرّب الرمز خارج قناة إرساله الحقيقية). الرمز يُرسل بالفعل من
  **spruvex-r نفسه** عبر `ResendOtpSender` الموجود مسبقًا هناك
  (`apps/api/src/modules/identity/otp/resend-otp-sender.ts`)، ويُفعَّل تلقائيًا فقط
  عندما تكون **نفس** متغيّر `RESEND_API_KEY` مضبوطًا على **خدمة spruvex-r نفسها**
  (راجع `identity.module.ts`: `useClass: process.env.RESEND_API_KEY ? ResendOtpSender
  : DevOtpSender`). دون ذلك، الرمز يُطبع فقط بسجلات spruvex-r (`DevOtpSender`) ولن
  يصل أي مستخدم حقيقي أبدًا. **هذا إعداد منفصل تمامًا عن `RESEND_API_KEY` بهذا
  المستودع** — يجب ضبط المتغير على المشروعين كليهما لتفعيل البريد بكل مكوناته.

⚠️ **`SPRUVEX_R_API_URL` و`SPRUVEX_SITE_API_KEY` لا يظهران بأي كود يعمل بالمتصفح
أبدًا** — كل استدعاء لـ spruvex-r يمر عبر Route Handlers من جانب السيرفر فقط
(`src/lib/spruvexR.ts`)، حتى نقطة التحقق من الرمز (`/auth/register/verify`) رغم أنها
لا تحتاج مفتاح API أصلاً بجانب spruvex-r — التزامًا بعدم كشف رابط الـ API الداخلي
للمتصفح إطلاقًا.

**معروف/متبقٍ**: لوحة تحكم spruvex-r ليس فيها بعد صفحة "رابط دخول مباشر" تستهلك
رمزًا من الرابط تلقائيًا — لذلك اعتمدنا مسار OTP الموجود فعليًا بدل رابط سحري غير
مبني. بعد التحقق الناجح، المستخدم يُحوَّل لرابط لوحة التحكم الأساسي (`dashboardUrl`)
لكنه سيحتاج التعامل مع صفحة الدخول العادية هناك لاحقًا لو احتاج جلسة جديدة (لا كلمة
مرور معروفة له — الحساب أُنشئ برمز عشوائي). تحسين لوحة spruvex-r لدعم دخول مباشر
بالكامل بعد التحقق (session cookie أو رابط استهلاك token) خطوة تالية جيدة، خارج
نطاق هذا المستودع.

### 2) الاشتراك المدفوع — تحويل بنكي يدوي (`/pay/[plan]` → `POST /api/payment-submission`)
يُخزَّن الطلب في جدول `payment_submissions` بحالة `pending` (قيد المراجعة)، مع صورة/PDF
الإيصال (إن وُجد) في `data/uploads/` خارج `public/`. صاحب المنصة يوافق/يرفض يدويًا من
`/admin`.

**جاهزية استبدال ببوابة دفع فعلية (Moyasar)**: تصميم الجدول يدعم هذا مسبقًا —
`payment_method` (حاليًا `'bank_transfer'`)، `provider_ref` (فارغ الآن، يُملأ بمعرّف
عملية البوابة لاحقًا)، ونفس حالات `pending/approved/rejected` تُستخدم لسجل دفعة بوابة
حقيقية (تُحدَّث تلقائيًا من Webhook بدل المراجعة اليدوية) — بدون أي تغيير على شكل
الجدول أو الصفحات. راجع التعليق فوق `createPaymentSubmission()` في
`src/lib/repositories/paymentSubmissions.ts`.

## ⚠️ ملاحظة نشر مهمة: قاعدة البيانات SQLite

`better-sqlite3` يخزّن البيانات في ملف `<DATA_DIR>/spruvex-site.db` على القرص
(و`<DATA_DIR>/uploads/` للإيصالات) — `DATA_DIR` قابل للضبط عبر متغير بيئة (افتراضيًا
`data/` بجذر المشروع للتطوير المحلي). هذا يعمل بشكل ممتاز على استضافة **Node.js دائمة**
مع تخزين دائم (VPS / Docker مع Volume، أو **Render Web Service مع Persistent Disk** —
انظر `render.yaml` وقسم النشر أدناه).

**لا يعمل بشكل موثوق على منصات Serverless عديمة الحالة مثل Vercel** لأن نظام الملفات
هناك مؤقت (يُمسح بين الطلبات/عمليات النشر). عند الانتقال لإنتاج فعلي على منصة
Serverless، استبدل طبقة `src/lib/db.ts` باتصال Postgres (مثلاً عبر Prisma) — دوال
الـ repositories (`createTrialSignup`, `createPaymentSubmission`, إلخ) مصممة كواجهة
مستقلة عن التخزين لتسهيل هذا الاستبدال دون تغيير أي صفحة أو نقطة API تستدعيها.

## النشر على Render

`render.yaml` بجذر المستودع (وليس داخل `spruvex-site/`) يصف خدمة Node واحدة
(`rootDir: spruvex-site`) مع Persistent Disk مثبَّت على `/var/data` لملف SQLite.

⚠️ **لم يُختبر بنشر فعلي على Render من هذه الجلسة** (لا وصول لحساب Render ولا لشبكة
render.com من هذه البيئة) — القيم مبنية على معرفة موثّقة بمواصفة Render Blueprint، لكن
تحققت محليًا من: أن `npm run build && npm run start` يعملان بنجاح من جذر `spruvex-site/`
تمامًا كما سيُشغَّلان على Render، أن `next start` يلتقط `$PORT` تلقائيًا (Render يضبطه)،
وأن `DATA_DIR` عند ضبطه لمسار مطلق (يحاكي `/var/data`) يُنشئ ملف قاعدة البيانات هناك
فعليًا لا بمجلد المشروع. راجع لوحة Render نفسها بعد أول نشر للتأكد من التفاصيل
الدقيقة (خصوصًا اسم الخطة اللازمة فعليًا لدعم Persistent Disk بحسابك) — التفاصيل
والقيود موثّقة كتعليقات مباشرة داخل `render.yaml`.

**المتغيرات الأربعة التالية `sync: false`** — يجب ضبطها يدويًا بلوحة Render (Environment)
بعد أول Blueprint sync، لا تُولَّد تلقائيًا ولا تُقرأ من أي ملف بالمستودع:
`SPRUVEX_R_API_URL`, `SPRUVEX_SITE_API_KEY` (يجب أن يطابق حرفيًا نفس القيمة بجانب
spruvex-r), `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`.

## الأمان والعزل

- **rate limiting** في الذاكرة على `/api/trial-signup` (+`verify`/`resend-otp`)،
  `/api/payment-submission`، و`/api/admin/login` (محدودية: عملية Node واحدة فقط —
  للنشر الموزّع استبدله بـ Redis/Upstash، موثّق في `src/lib/rateLimit.ts`). هذا فوق
  حد spruvex-r نفسه (5 طلبات/ساعة لكل IP على `/public/trial-signup`) — طبقتا حماية
  مستقلتان.
- **تحقق مدخلات صارم** عبر Zod: صيغة جوال سعودي، بريد إلكتروني، حدود طول النصوص.
- **رفع الإيصال**: التحقق من نوع الملف الحقيقي عبر توقيع الملف (magic bytes) وليس
  الامتداد (`src/lib/fileValidation.ts`)، حد أقصى 5MB، تخزين خارج `public/` باسم UUID
  عشوائي، ويُخدَّم فقط عبر `/api/admin/receipt/[id]` بعد التحقق من جلسة إدارة صالحة —
  لا رابط عام قابل للتخمين أبدًا.
- **بيانات شخصية**: طلبات التجربة والتحويل (اسم مطعم، جوال، بريد) لا تظهر بأي صفحة
  عامة إطلاقًا — فقط عبر `/admin` بعد تسجيل الدخول.
- **CSRF**: نمط double-submit عبر كوكي `csrf_token` (httpOnly، يُصدره `proxy.ts`)، تتحقق
  منه كل نقطة POST قبل أي كتابة بقاعدة البيانات.
- **XSS**: كل المحتوى يُعرض عبر React (تهريب تلقائي)، لا استخدام لـ
  `dangerouslySetInnerHTML` في أي مكان بالمشروع، بما فيه لوحة الإدارة.
- **جلسة الإدارة**: JWT موقّع (HS256 عبر `jose`) بكوكي httpOnly، صلاحية 12 ساعة،
  كلمة المرور تُقارن بمقارنة زمن ثابت (`timingSafeEqual`) لمنع Timing attacks، ومحاولات
  الدخول محدودة (8 محاولات / 15 دقيقة لكل IP).
- **رؤوس أمان أساسية** (`X-Frame-Options`, `X-Content-Type-Options`, إلخ) عبر `proxy.ts`.

## الحسابات والتفعيل — الحالة الفعلية الآن

- **التجربة المجانية**: تفعيل **تلقائي فوري** عند نجاح الاستدعاء لـ spruvex-r (الحالة
  الشائعة). يبقى تفعيلًا يدويًا فقط كخطة بديلة عند فشل الاستدعاء (`manual_review`
  بلوحة `/admin`) — راجع القسم أعلاه.
- **الاشتراك المدفوع (تحويل بنكي)**: يدوي بالكامل حتى الآن — يحتاج مراجعة وتفعيل من
  فريق SpruVex عبر `/admin` دائمًا (لا بوابة دفع فعلية بعد).
